# Further Mathematics — Stage 1

Сквозной скелет из `files/ROADMAP.md`: одна задача проходит весь путь от схемы
базы до `part_response` и обратно. Целевая архитектура — в `files/SYSTEM-DESIGN.md`,
ссылки на её разделы (§) расставлены прямо в коде и в миграциях.

## Запуск

```bash
npm install && cp .env.example .env.local && npm run db:up && npm run db:reset && npm run dev
```

Приложение — на `http://localhost:3100`, Postgres — на `5439` (порты 5432–5436
на этой машине заняты другими проектами; меняются в `docker-compose.yml` и `.env.local`).

Демо-вход (пароль у всех `password123`):

| Роль | Почта |
|---|---|
| Учитель | `teacher@example.com` |
| Ученик | `student@example.com` |

Планы на Stage 2–4 — в `files/ARCHITECTURE-STAGES-2-4.md`. Там же зафиксировано
расхождение между `files/ROADMAP.md` (написан под SAT) и `files/SYSTEM-DESIGN.md`
(написан под Further Maths) — его надо закрыть до начала Stage 2.

## Роли и экраны

| Путь | Кто | Что |
|---|---|---|
| `/` | все | витрина; вошедшего сразу уводит в его раздел |

| `/bank` | все | банк задач с фильтром по комиссии |

| `/learn` | ученик | выданная домашка со статусами |
| `/learn/[id]` | ученик | задачи внутри задания |
| `/teach` | учитель | классы с кодами вступления |

Пароли хешируются `scrypt` из `node:crypto` — без нативных зависимостей,
которых не должно быть на serverless-хостинге. В базе лежит только хеш токена
сессии: дамп базы не даёт войти под чужим аккаунтом.

## Проверка

```bash
npm run check:invariants
```

Прогоняет банк через ту же функцию, что блокирует публикацию, и собирает
весь LaTeX тем же кодом, что рендерит страницу — под каждым профилем
обозначений отдельно.

```bash
npm run demo:classroom
```

Учебный цикл целиком: учитель входит, создаёт класс, ученик вступает по коду,
учитель выдаёт домашку, ученик решает, учитель видит журнал. Отдельно проверяет,
что чужой класс и чужая попытка недоступны, и главное правило разбора: одна
и та же задача в домашке и в свободной практике — две разные попытки,
и открытый разбор в практике не разблокирует домашку.

```bash
npm run demo:walkthrough
```

Сквозной прогон по HTTP: создаёт попытку, отвечает на все пять оцениваемых
частей смесью верного и неверного, забирает разбор и проверяет, что ключи
ответов не уехали в HTML. Ожидаемый итог — 4 из 8.

```bash
npm run demo:regrade
```

Автор занёс в ключ `BA` вместо `AB`, ученик ответил верно и получил ноль.
Скрипт публикует версию 2 с исправленным ключом и переигрывает сохранённый
ответ: 0 → 2 балла, с записью в журнале пересчётов.

## Что здесь есть

**Две таксономии** (`001_taxonomy.sql`). Концепты board-agnostic, пункты
спецификаций board-specific, между ними many-to-many. Задача привязана
к концептам и не знает про комиссии; список для Edexcel собирается обратным
обходом в `listItemsForBoard`. Переключите комиссию на главной: одна и та же
строка банка покажется как `CP1 · 2.1` и как `FP1 · 1.4`, а `\vect{M}`
отрендерится жирным или подчёркиванием.

**Задача как версионируемый документ** (`002_items.sql`). Части принадлежат
версии, а не задаче — поэтому `part_id` сам по себе несёт версию, и попытка
ученика намертво связана с тем, что он видел. Подпункты `(b)(i)` — через
`parent_part_id` и стабильный `path`.

**Блокирующая валидация** (`004_publish_invariants.sql`). `item_version_publish`
не пропустит версию, где сумма баллов по частям расходится с заявленной, где
схема оценивания недобирает или перебирает баллы, где нет концепта. Триггер
`item_version_freeze` не даёт править опубликованную версию. Правило живёт
в базе: и форма автора, и будущий YAML-импорт пройдут через одну проверку.

**Сырой ответ рядом с версией проверяльщика** (`003_attempts.sql`).
В `part_response` лежит то, что ввёл ученик, `graded_against_part_id`
указывает на часть, чьим ключом это проверили, а `marks_awarded` —
генерируемый столбец `coalesce(override_marks, auto_marks_awarded)`:
учительская правка и машинный балл хранятся раздельно.

**Разбор закрывается на сервере.** `GET /api/items/{slug}/solution` принимает
`attempt_id` и решает по контексту попытки. Без контекста ответить нельзя:
одна задача бывает одновременно в домашке и в свободной практике.

## Чего здесь нет

Ролей и входа (Stage 3), классов и назначений (Stage 3), CAS на SymPy
и типов `symbolic` / `complex` (Stage 4), аналитики по концептам (Stage 5),
авторского редактора (Stage 2). `regrade` написан как функция, а не как
задача pg-boss — воркер приезжает на Stage 4.

Из типов ответов работают `mcq`, `matrix` и `numeric`. Остальные возвращают
`UNSUPPORTED_ANSWER_TYPE` явно, а не молчаливый ноль.

## Раскладка

```
db/migrations/     SQL, применяется по порядку; схема читается отсюда
db/seed.mjs        две комиссии, дерево концептов, одна задача Core Pure 1
src/lib/grade.mjs  грейдеры; plain-JS, общий для API и скрипта пересчёта
src/lib/tex.mjs    KaTeX на сервере; общий для рендера и валидатора банка
src/lib/regrade.mjs        переигрывание сохранённых ответов
src/lib/versioning.mjs     новая версия задачи из существующей
src/lib/solution-gate.ts   правило показа разбора
scripts/           валидатор банка и два демонстрационных прогона
```

`grade.mjs` и `tex.mjs` намеренно plain-JS: их импортируют и Next, и скрипты
на голом node. Грейдер, который «похож» на боевой, однажды разойдётся с ним
и пересчёт выставит не те баллы.
